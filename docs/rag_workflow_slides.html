Molecular Cell Biology RAG：带证据的论文问答系统

目标不是让 GPT “凭记忆回答”，而是让它先从本地论文资料库里找证据，再基于证据组织中文答案；副凋亡只是当前验证用的第一个主题。

1 / 6 总览

一句话解释 RAG

  • Retrieval：先找资料。
  • Augmented：把找到的资料交给 GPT。
  • Generation：GPT 只根据这些资料回答。
对听众可以这样说：这不是“让 AI 自己想答案”，而是“让 AI 带着论文证据回答”。
输入用户问题，例如“副凋亡能克服耐药吗？”
中间过程从本地论文库中找最相关证据。
输出中文答案 + 引用到具体 node_id。
保护机制证据不足时提示风险或说证据不足。

第一步：把论文变成可检索的资料库

系统先从公开数据库收集论文身份信息、摘要和全文 XML，然后把长论文切成小段，并把每段文字转换成向量，方便后续语义检索。

2 / 6 数据准备

这里最重要的是两件事：一是“身份”和“内容”分开；二是每个 chunk text 会被 embedding model 转换成 vector，之后才能做语义检索。

为什么要这样设计？

  • 同一篇论文可能同时有 DOI、PMID、PMCID，需要去重合并。
  • 摘要很有价值，但不能混进正文段落里。
  • 全文里有 methods、results、discussion 等章节，回答时可以过滤 methods。
  • 每个 node 都保留 content_type 和 section_type，方便审计。
  • 每个 chunk 还会被 embedding model 转成 vector，存入本地 LlamaIndex。

当前保留的内容类型

类型用途
abstract短、信息密度高，适合快速回答概览问题。
fulltext更详细，适合机制、通路、证据链问题。
vector不是给人读的文本，而是模型用来比较“语义距离”的数字表示。

第二步：用户提问时，系统如何找证据？

中文问题会先改写成英文检索问题，因为论文主体是英文；语义检索时，query 也会被转换成 vector，再和资料库里的 chunk vectors 做相似度比较。

3 / 6 Hybrid Retrieval

关键词检索像“查目录”；语义检索先把文字变成 vector，再找向量空间里距离近的片段，也就是“意思相近”的段落。

为什么要 Hybrid？

  • 只用关键词：容易抓到字面匹配但语义弱的结果。
  • 只用语义：vector 能抓意思接近的段落，但可能漏掉基因名、药名这类精确实体。
  • Hybrid 同时利用两者：先广泛召回，再综合排序。
  • 默认更信任语义分数：embedding 权重 0.8，BM25 权重 0.2。

默认保护

情况处理
只被关键词找到分数乘以 0.4，避免字面噪声冲太高。
只被语义找到分数乘以 0.8，保留但略降权。
两边都找到不惩罚，说明结果更稳定。

我们用什么 embedding model？

当前使用 HuggingFace 上的生物医学 embedding model：pritamdeka/S-PubMedBert-MS-MARCO。它把 query 和论文 chunk 都转换成向量，用于比较语义相似度。

4 / 6 Embedding Model

向量可以理解成“文本在语义地图上的坐标”。医学含义接近的文本，坐标距离通常更近。

为什么不用通用 embedding？

  • 分子细胞生物学里有大量专业词：基因、蛋白、通路、药物、细胞死亡类型。
  • 通用模型可能知道词面，但不一定能稳定表示生物医学语义。
  • PubMedBERT 系列是在生物医学文献语料上训练，更适合论文检索。
  • S-PubMedBert-MS-MARCO 适合把 query 和文档片段映射到同一个向量空间。

我们怎么用它？

阶段用途
build index把每个 chunk text 转成 vector，存到本地 LlamaIndex。
retrieve把 query 转成 vector，找最相似的 chunk vectors。
offline默认优先用本地缓存，避免每次访问 HuggingFace Hub。

第三步：GPT 如何生成答案？

GPT 看到的是原始问题、英文检索问题、以及 Top 8 证据片段；系统要求它只基于这些证据回答。

5 / 6 Answering

输入给 GPT 的内容

字段作用
Original query用户原始问题，中文问题最终也用中文回答。
Normalized query英文检索问题，用来说明检索意图。
Evidence nodes每条证据包含 node_id、标题、章节、正文片段。
System rules只基于证据回答；证据不足就说不足；关键结论必须标注 node_id。
这样做的目的：减少幻觉，让答案能被人工追溯到具体论文片段。

输出长什么样？

  • Answer：中文机制性回答。
  • Evidence：列出 node_id、标题、章节、分数和预览。
  • content_type：说明证据来自 abstract 还是 fulltext。
  • year / cited_by_count：如果 metadata 里有，就一起展示。
高质量回答结论具体，且每个关键点都有出处。
低质量回答证据偏题、只检到一边，或泛泛而谈。
证据不足应该明确说 insufficient，而不是编。
人工可查通过 node_id 回到原始 chunk。

回答前先看两个诊断指标

指标含义为什么重要
Retrieval strength由 top1 和 top5 分数计算。判断是否找到了强相关证据；不被 coverage 降级。
Evidence diversity前 8 条证据来自多少不同 PMCID。区分“多篇文章支持”和“核心论文集中命中”。
query_coverage重要 query terms 是否出现在证据里。单独展示为诊断指标，但不参与 HIGH / MEDIUM / LOW。

我们如何评测这个 RAG 是否真的有用？

评测不是自动打分，而是生成对照报告，让人比较 GPT-only 和 RAG 在正确性、具体程度和证据支持上的差异。

6 / 6 Evaluation

问题集覆盖什么？

  • HIGH：RAG 应明显优于 GPT，例如 ER stress、PI4KB、耐药、预后。
  • MEDIUM：常识性比较题，例如副凋亡 vs 铁死亡、焦亡、自噬。
  • LOW：当前 corpus 外或无关问题，例如神经退行性疾病、天气、股票。
  • Stress test：中文改写是否能正确映射到英文检索意图。

最终看什么？

维度人工判断重点
正确性答案是否符合论文证据。
具体程度是否给出机制、通路、药物或基因细节。
证据支持关键结论后是否有可靠 node_id。
拒答能力资料不足或问题无关时，是否避免硬答。
